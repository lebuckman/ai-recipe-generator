# AI Recipe Generator

A serverless web app that turns a list of ingredients into a recipe idea:
- Users sign up with an email address and sign in.
- They type ingredients such as `chicken, white rice, yellow squash, onion`.
- The app returns a recipe generated by **Claude Haiku 4.5** on **Amazon Bedrock**.

It's built with **React + TypeScript (Vite)** on the frontend and an **AWS Amplify Gen 2** backend: Cognito for sign-in, AppSync for a GraphQL API, and Bedrock for the model.

The project follows the AWS hands-on tutorial [Build a Serverless Web Application using Generative AI](https://docs.aws.amazon.com/hands-on/latest/build-serverless-web-app-lambda-amplify-bedrock-cognito-gen-ai/build-serverless-web-app-lambda-amplify-bedrock-cognito-gen-ai.html), updated for a current toolchain and model (see [Changes from the tutorial](#changes-from-the-tutorial)).

> **Status:** deployed and tested on Amplify Hosting in `us-east-2`, then torn down after testing to avoid leaving a public endpoint that calls a paid model. Follow [Deploy](#deploy-amplify-hosting) to bring it back.

## How it works

```
┌──────────────────────────┐   1. sign up / sign in        ┌──────────────────────┐
│  React app (Vite)        │ ────────────────────────────► │  Amazon Cognito      │
│  <Authenticator> wrapper │ ◄──────────────────────────── │  user pool           │
│                          │      JWT tokens               └──────────────────────┘
│  askBedrock(ingredients) │
│                          │   2. GraphQL query + token    ┌──────────────────────┐
│                          │ ────────────────────────────► │  AWS AppSync         │
│                          │                               │  auth: signed-in     │
│                          │                               │  users only          │
│                          │                               │  resolver: bedrock.js│
│                          │                               └──────────┬───────────┘
│                          │                                          │ 3. HTTPS, signed (SigV4)
│                          │                                          │    with the data source's
│                          │                                          │    IAM role
│                          │                               ┌──────────▼───────────┐
│                          │   4. { body: "recipe…" }      │  Amazon Bedrock      │
│  renders the result      │ ◄──────────────────────────── │  Claude Haiku 4.5    │
└──────────────────────────┘                               │  (US inference       │
                                                           │   profile)           │
                                                           └──────────────────────┘
```

1. **Auth.** The `<Authenticator>` component from `@aws-amplify/ui-react` wraps the app.
   - It provides sign-up, sign-in and email verification (a 6-digit code) through a Cognito user pool.
   - Nothing else renders until the user is signed in.
2. **API.** The client from `generateClient<Schema>()` calls the `askBedrock` query with the user's Cognito token. AppSync rejects callers who aren't signed in (`allow.authenticated()`).
3. **Model call.** No Lambda function is involved.
   - The query's resolver, `amplify/data/bedrock.js`, runs inside AppSync. It builds an HTTP request to Bedrock's `InvokeModel` endpoint.
   - An **HTTP data source** sends that request, signed with an IAM role that may invoke exactly one model.
4. **Result.** The resolver pulls the text out of Claude's response, or passes Bedrock's error message along. The UI displays the result.

The browser never calls Bedrock directly and holds no credentials that can. It calls `askBedrock` with a Cognito token, and only AppSync's IAM role can reach the model.

```

```

## Getting started (local development)

### Prerequisites

- **Node.js 20.19+ or 22.12+** (Vite 8) and npm.
- **An AWS account** with Bedrock access to **Claude Haiku 4.5** in a US region.
  - Anthropic models need a one-time "use case details" form per account. Running a prompt in the Bedrock playground triggers it.
- **AWS credentials** for the CLI and Amplify tooling. For example:
  ```bash
  aws login
  ```
  If the Amplify CLI can't find those credentials, export short-term ones into the shell:
  ```bash
  eval "$(aws configure export-credentials --format env)"
  ```
- **CDK bootstrap:** the first sandbox deploy in a region asks for this one-time step. Follow the link it prints.

### Run

```bash
npm ci
npx ampx sandbox        # deploys a personal cloud backend and writes amplify_outputs.json; leave it running
```

In a second terminal:

```bash
npm run dev
```

Open the local URL, choose **Create Account**, confirm the emailed code, and generate a recipe.

**About the sandbox:**
- It's a full, separate copy of the backend (user pool, API, roles) that belongs to one developer.
- It watches `amplify/` and redeploys on save.
- Delete it with `npx ampx sandbox delete`.

## Deploy (Amplify Hosting)

1. **Push this repo to GitHub.**
2. **Amplify console** → **Create new app** → **GitHub**.
   - Authorize the AWS Amplify GitHub App for **this repository only**.
   - Choose the `main` branch.
3. **Create a service role.** In IAM, create a role:
   - trusted entity: **AWS service → Amplify → Amplify - Backend Deployment**;
   - permissions policy: `AmplifyBackendDeployFullAccess`.

   Then attach it under the app's **App settings → IAM roles → Service role**. Without it, the backend phase can't deploy.
4. **Push to `main`.** `amplify.yml` runs on every push:
   - **backend phase:** `npm ci`, then `npx ampx pipeline-deploy`. This deploys a separate backend for the branch and generates `amplify_outputs.json` during the build.
   - **frontend phase:** `npm run build`, then publishes `dist/`.
5. **Open** `https://main.<app-id>.amplifyapp.com`.
   - The branch backend has its own user pool, so accounts made against the sandbox don't carry over.

## Configuration

| What | Where |
|---|---|
| Model | `MODEL_ID` in `amplify/data/bedrock.js` **and** `MODEL` in `amplify/backend.ts` (the IAM policy). They must match. |
| Prompt | the `prompt` template in `amplify/data/bedrock.js` |
| Response length / cost cap | `max_tokens` in `amplify/data/bedrock.js` (currently 1000) |
| Region | taken from the deployed stack (`Stack.of(...).region`). Change the AWS profile region to deploy elsewhere. |
| Sign-in method and email text | `amplify/auth/resource.ts` |

**To change models:**
- Use an **active** model ID, or an **inference profile** ID (`us.` / `global.` prefix).
- The IAM policy needs to allow the profile **plus** the underlying model in every region that profile can route to. List those regions with:
  ```bash
  aws bedrock get-inference-profile --inference-profile-identifier <profile-id>
  ```

## Changes from the tutorial

| Tutorial | This repo | Why |
|---|---|---|
| Claude 3.5 Sonnet v2 (`anthropic.claude-3-5-sonnet-20241022-v2:0`) | Claude Haiku 4.5 via `us.anthropic.claude-haiku-4-5-20251001-v1:0` | The tutorial's model has reached end of life on Bedrock and rejects calls. Haiku 4.5 is also cheaper per token. |
| `us-east-1` written into the endpoint, signing region and policy ARN | Region and account read from the CDK stack | Deploys in any region (here `us-east-2`). Keeps the account ID out of a public repo. |
| IAM policy on one foundation-model ARN | Policy on the inference profile and the model in `us-east-1`, `us-east-2`, `us-west-2` | Inference profiles route between regions, and each possible target must be allowed. |
| Resolver parses `content[0].text` unconditionally | Returns `{ error }` on non-200 responses, and the UI shows it | Bedrock errors such as access denied become readable messages instead of a parse failure. |
| `main.tsx` imports `./App.jsx` | Imports `./App.tsx` | Matches the actual filename. Optional: the build also resolves `./App.jsx` to the `.tsx` file. |
| Plain `import` of types | `import type { Schema }`, `type FormEvent` | Required by the Vite template's `verbatimModuleSyntax`. Otherwise `npm run build` fails. |
| No `resolveJsonModule` | Added to `tsconfig.app.json` | Makes the `amplify_outputs.json` import explicit. Optional: it type-checks without the flag under `moduleResolution: bundler`. |
| Default (frontend-only) Amplify build settings | `amplify.yml` with a backend phase, plus a service role | Without them, the hosted build has no backend and no `amplify_outputs.json`. |
| (none) | `overrides` in `package.json` for `@aws-cdk/toolkit-lib` and `@opentelemetry/core` | Amplify's packages pin conflicting versions of these. `npm install` tolerates that, but `npm ci` (used in CI) rejects the lockfile. |

## Cost

Everything is pay-per-use. **An idle deployment costs about $0.**

| Service | Pricing basis | This project |
|---|---|---|
| Bedrock (Haiku 4.5) | about $1 per million input tokens, $5 per million output tokens | about $0.005 per recipe at most (`max_tokens: 1000`) |
| AppSync | per million queries and data transfer | fractions of a cent |
| Cognito | per monthly active user, with a free allowance | free at this scale |
| Amplify Hosting | build minutes, storage, data served | cents |

## Security notes

- **Least privilege.** AppSync's data source role may call `bedrock:InvokeModel` on one model and nothing else.
- **No AWS secrets in the client or the repo.**
  - `amplify_outputs.json` is gitignored but bundled into the frontend, so treat everything in it as public: the user pool and identity pool IDs, the API URL, and the AppSync API key.
  - The account ID is looked up when the stack deploys, never written in the code.
- **Identity pool.** `defineAuth` also creates a Cognito identity pool with guest access enabled, which can issue temporary AWS credentials to the browser. The app's code doesn't use them, and no permissions were added to those roles.
- **Public sign-up.** Anyone can create an account and spend Bedrock tokens. Before leaving this deployed long-term, add:
  - per-user rate limiting or quotas;
  - input length validation;
  - AWS WAF on the AppSync API;
  - a budget alert.
- **Unused API key.** The data schema's default authorization mode is an API key (30-day expiry), but `askBedrock` accepts only signed-in users. The app never uses the key, but it ships in the client bundle, so any operation later opened to API-key access would be public.

## Clean up

```bash
npx ampx sandbox delete
```

In the Amplify console: **App settings → General settings → Delete app**. This deletes the hosted app and its branch backend.

Optionally, also:
- delete the Amplify service role;
- remove the AWS Amplify GitHub App's access to the repo.

## Possible improvements

- **Render Markdown.** Claude answers in Markdown, and the app currently shows raw `#` and `**`. `react-markdown` would render it.
- **Stream responses** (Bedrock `InvokeModelWithResponseStream` through a Lambda function or AppSync subscriptions) so text appears as it's generated.
- **Structure the output.** Request JSON (title, ingredients, steps, time) and render it as a recipe card.
- **Recipe history.** Store generated recipes for each user in a DynamoDB-backed `a.model()` with owner-based authorization.
- **Input validation and quotas** in the resolver.
